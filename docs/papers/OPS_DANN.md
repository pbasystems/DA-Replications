# What is OPS-DANN
OPS-DANN (Operation Profile-specific DANN) is a domain-adversarial network for RUL prediction that assigns a separate domain discriminator to each flight operation phase (ascending/steady/descending), rather than a single discriminator over the whole sequence. The model is based on the paper "Domain Adaptation via Alignment of Operation Profile for Remaining Useful Lifetime Prediction", Nejjar et al. (2023), targeting the N-CMAPSS dataset. This implementation covers the **OPS-DANN Hard** variant only (one discriminator per phase, hard-assigned).

# What Missing
- **Training instability / mode collapse, not yet root-caused.** Running `run_ops_dann_experiment.py`'s 10-trial average for S→L (FC1→FC3) gives RMSE `13.65 ± 2.82` / s-score `3.57 ± 0.70`, far worse than the paper's Table 3 (`3.90 ± 0.56` / `1.39 ± 0.10`). A controlled diagnostic (3 seeds) showed the run splits cleanly into two outcomes: ~1/3 of seeds converge to numbers close to the paper (RMSE ~4.2-4.6), while ~2/3 collapse to a degenerate fixed point where the regressor predicts a constant equal to the batch-mean RUL regardless of input (`rul_pred` std of exactly `0.0` after training; `rul_loss` never leaves its epoch-1 level of ~0.25-0.28 across all 15 epochs). This was tested against two candidate fixes — Xavier normal initialization (which the paper specifies but this codebase doesn't apply) and gradient-norm clipping at 1.0/5.0 (which `LSTM_DANN`'s `Trainer` has but `OPS_DANN`'s doesn't) — neither changed which seeds collapse, and collapsed seeds land on nearly identical RMSE (`14.69`/`14.70`) regardless of which fix was applied. This points to the adversarial pressure (`ρ` already reaches `0.32` by the end of epoch 1 and `0.93` by epoch 5, driven by `tradeoff=1.0` applying at full strength from the start) overwhelming the RUL task before it has learned anything, likely depending on batch shuffle order rather than weight initialization — but the exact mechanism is unconfirmed. Root cause and fix are still open.
- The paper performs a grid search over Table 2's hyperparameter space per method, using the S→L task's optimum for all three tasks. This codebase hardcodes that one S→L-optimal row (`lr=0.05`, `momentum=0.5`, `tradeoff=1.0`) — no grid search is implemented.
- The paper reports Table 3 as "Mean ± Std" but never states the trial count (unlike the LSTM-DANN paper's explicit "10 trials"). `run_ops_dann_experiment.py` defaults to 10 trials to match that other paper's convention — this is an assumption, not something read off this paper.
- Only the S→L task is wired up end-to-end (`ops_main.py`, `run_ops_dann_experiment.py`). S→M (25 epochs) and M→L (15 epochs) use different epoch counts per the paper and aren't currently runnable without editing constants by hand.
- OPS-DANN Soft and Multi-Class OPS-DANN (the paper's other two variants) are not implemented — only OPS-DANN Hard.
- No Proxy A-Distance (PAD) evaluation (Section 4.7 / Figure 9) is implemented, so representation transferability can't be checked independently of RMSE/s-score.
- All models should be initialized with Xavier normal initialization per Section 4.5; none of the `Model` classes apply this (see the mode-collapse finding above — this alone did not fix it, but the deviation from the paper's stated procedure is still present).

# Assumptions
- Fault onset is detected via the `hs` health-state flag (`1`=healthy, `0`=faulted), verified empirically against N-CMAPSS DS03 to flip cleanly and monotonically exactly once per unit. The paper's degradation parameters (`T`) are nonzero from cycle 1 (they include "normal" linear degradation too), so they can't be used for this instead.
- RUL is normalized per unit as `(raw RUL) / (raw RUL at the first post-onset sample)`, giving exactly `1.0` at fault onset and `0.0` at end-of-life, matching the paper's stated "decrease from one to zero between the point in time when the fault occurs and the end of life." The raw onset value is retained per-window (`Dataset.rul_scale`) purely so predictions/targets can be un-normalized back to raw cycle units — necessary because the paper's Table 3 RMSE/s-score are reported in raw cycles, not on the `[0,1]` normalized scale the model is actually trained on. Cross-checking against actual `rul_onset` values (range 35-58 cycles across DS03's 15 units) supports this reading over an earlier, incorrect "×100 percentage points" guess.
- The paper's Eq. 15 NASA score is a **sum** over samples (`s = Σ exp(α|ŷ-y|)`), but Table 3's reported `s-score` values (e.g. `1.39`) are far too small to be a raw sum over ~362k windows. Dividing the implementation's raw summed score by `n_samples` gives a per-sample mean that lines up closely with Table 3 (e.g. `1.50` vs. the paper's `1.39` for OPS-DANN Hard S→L) — read as the paper reporting a per-sample average despite Eq. 15's literal sum notation.
- Operation phases (ascending/steady/descending) are labeled via the altitude derivative thresholded at `0.5 ft/s` (Eq. 8) plus a length-51 median filter, both matching the paper's stated values.
- Downsampling decimates the continuous feature channels with a Chebyshev/IIR filter (order 8, matching the paper), while accompanying per-sample fields (cycle, `hs`, RUL, unit) are simple stride-based subsampled rather than filtered, since they're step/monotonic signals rather than something to low-pass filter.
- Feature normalization is min-max to `[-1, 1]`, fitted on the source domain only and reused for the target domain, matching the paper's "scaler was fitted on the source domain data... and subsequently applied to the target domain data."
